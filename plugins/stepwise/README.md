# stepwise

Referencia detallada del plugin `stepwise`: el flujo de desarrollo paso a paso con Claude Code, con ramas y Sub-PRs, trazabilidad por paso, agentes y hooks. La introducción en inglés está en el [README raíz](../../README.md), y las decisiones de diseño, en [el documento de decisiones](../../docs/decisions/bootstrap/business-rules.md).

Las piezas no leen configuración: delegan en `## Project commands` del `CLAUDE.md` del proyecto y, si falta un dato, se detienen y proponen la línea.

## Contenido
- `agents/test-runner.md` (Haiku; Bash): agente delgado. Con los modos `step <rutas>` (`Tests (step)`) y `full` (`Tests (full)`), hace una sola llamada en primer plano a `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run_tests.py" <modo> [rutas]` y devuelve su salida sin cambiarla. No lee `CLAUDE.md` ni parsea nada: el contrato, la ejecución, el timeout y el reporte son del script (ver **Corrida de tests**). Si Claude Code pasa su Bash a segundo plano (en las sesiones interactivas, de VS Code o de la CLI, a los 180 s; en `claude -p`, no), espera el aviso de que terminó y lee el final de la salida con `tail -n 20`. `${CLAUDE_PLUGIN_ROOT}` lo sustituye Claude Code en el cuerpo del agente; no está en el entorno de Bash.
- `agents/explore.md` (Sonnet; Read, Grep, Glob): búsquedas de solo lectura, sin shell. Devuelve conclusiones con `ruta:línea`, en 30 líneas como máximo.
- `agents/code-reviewer.md` (Opus; Read, Grep, Glob, Bash de solo lectura): revisa un diff (local o `gh pr diff`) contra el ADR del feature, el `CLAUDE.md` y los `README.md` de las carpetas tocadas. Revisa criterios sin test, bugs, seguridad, llamadas externas en transacciones, concurrencia, convenciones y alcance. Devuelve hallazgos `blocker`, `suggestion` o `question` con `ruta:línea` y arreglo, en 60 líneas como máximo. En la segunda pasada revisa solo los arreglos que recibe. Nunca edita, ni hace commit, ni publica. El "solo lectura" de Bash está en sus instrucciones, porque `tools` no restringe por patrón.
- `skills/spec/` (`/spec <descripción>`): clasifica el pedido (feature, bug o paso nuevo), investiga con `explore`, entrevista solo sobre lo que el código no responde (4 preguntas por ronda; en `-p`, en texto plano) y escribe el ADR con su plantilla (`references/decision-template.md`): `CA-n` en Dado / Cuando / Entonces, pasos con sus CA, fuera de alcance, riesgos y decisiones abiertas, en 150 líneas como máximo. Con aprobación, crea `<feature>` desde `Base branch` sin upstream (`--no-track`), hace commit y push del ADR y abre el PR principal en draft (con un remoto que no es de GitHub, lo salta). Nunca escribe código.
  - **Prompt del pedido** (clave opcional `- Prompts: docs/prompts/<feature>/`): después de la aprobación, `/spec` escribe el texto exacto con el que se invocó, sin resumirlo ni recortarlo, en `<Prompts>/<AAAA-MM-DD>-spec.md` (feature o bug) o `<AAAA-MM-DD>-spec-step-<n>.md` (paso nuevo; `<n>` es el primer paso que agrega). Encima va un encabezado con la fecha, el tipo, la rama y el enlace al ADR. Entra en el mismo commit del ADR, y "Fuente / Documento" lo enlaza.
    - Si el archivo ya existe, no lo sobrescribe: se detiene antes del commit y pregunta si lo sobrescribe, usa otro nombre o no lo guarda.
    - No mira el largo de la ruta: el límite es de cada proyecto (en este repo, `tests/test_path_lengths.py`).
    - Sin la clave, no guarda nada; el resumen de aprobación y el reporte lo dicen en una línea.
- `skills/implement/` (`/implement <n>`): comprueba el árbol, la rama `<feature>`, el paso y que el anterior esté mergeado; crea `<feature>-step-<n>`. Por cada CA, test primero (en un bug, guarda la evidencia de que el CA de regresión falla antes del arreglo y cuáles pasaban), luego el código, y los tests del paso con `test-runner`; con `Tests (step): none`, o en un CA marcado `(manual: <motivo>)`, una verificación manual (ver abajo). Corre `Lint/format` y `Type check`. Si el ADR tiene un hueco, se detiene y propone el cambio. Si el paso agrega, borra o cambia algo en `.claude/agents/`, `.claude/skills/` o `.claude/commands/`, el reporte pide abrir una sesión nueva, porque la sesión sigue cargando los de antes. No hace commit.
- `skills/check/` (`/check`): suite completa con `test-runner`, `Migrations check`, `Lint/format` y `Type check`; un fallo de cualquiera es un fallo del paso. Si falla, arregla solo lo del paso, vuelve a correr `Lint/format` y `Type check`, con 3 intentos como máximo, y pregunta antes de tocar un fallo que parece preexistente. Al pasar, escribe la sección "Pruebas" de la trazabilidad con la huella del paso (y, con `Docs paths`, la huella de código) y la alineación del plugin (ver abajo), sin commit.
- `skills/audit/` (`/audit self | comments [<num>] | pr <num>`):
  - `self`: el diff local del paso con `code-reviewer`; arregla los `blocker`, pregunta una vez por las sugerencias y las preguntas, revisa solo los arreglos en una segunda pasada y escribe "Code review" en la trazabilidad. Lo corre `/close`.
  - `comments`: trae con `gh` los comentarios sin resolver del PR (por defecto, el principal), los verifica contra el código y los clasifica en `válido`, `no aplica` o `requiere decisión`. Con aprobación, los válidos se vuelven un paso "Atender review" del ADR (PR abierto) o una feature nueva con `/spec` (PR mergeado).
  - `pr <num>`: revisa el PR de otra persona y redacta comentarios en línea y un resumen; el veredicto lo elige el usuario.
  - Nunca publica en GitHub sin aprobación explícita.
- `skills/close/` (`/close`): exige "Pruebas" (si falta, pide `/check`). Corre `/audit self`, salvo que su última ronda tenga la misma huella y ningún `blocker` abierto. Si la huella cambió desde `/check`, vuelve a correr la suite, `Migrations check`, `Lint/format` y `Type check` antes del commit; si solo cambiaron rutas de `Docs paths` (ver la huella de código), corre solo `Lint/format` y `Type check`. Completa la trazabilidad con sus plantillas (`references/`), hace un commit, push sin `-u`, Sub-PR a `<feature>` con `--merge` y marca el paso en el PR principal, con las verificaciones `después del merge` como casillas. En el último paso escribe la descripción del PR principal y pregunta antes de sacarlo de draft; no lo saca mientras quede una de esas casillas sin marcar, salvo que el usuario lo diga. Con un remoto que no es de GitHub, hace el push, avisa y salta los pasos de `gh`.
- **Huella del paso** (`skills/close/scripts/fingerprint.py`): sha256 del diff contra `<feature>` con los archivos sin seguimiento, sin la trazabilidad ni el ADR. Solo lee. La anotan `/check` (en "Pruebas") y cada ronda de `/audit self` (en "Code review"); `/close` la recalcula para no repetir trabajo sobre el mismo diff.
  - **Huella de código** (`--docs <pathspecs>`): con la clave opcional `- Docs paths: '*.md' 'docs/**'` en `## Project commands` (pathspecs de git simples, sin magia como `:(glob)` o `:!`: el script los rechaza), `/check` anota también `Huella de código`, que deja fuera esas rutas. El `CLAUDE.md` de la raíz cuenta siempre, porque tiene el contrato. Si después de `/check` solo cambiaron esas rutas, `/close` no repite `Tests (full)` ni `Migrations check`. Sin la clave, todo sigue igual.
  - **Qué va en `Docs paths`:** solo rutas que ningún test, lint de código ni migración lee. Un proyecto donde los `.md` son parte del producto (como este repo, cuyas skills y agentes son `.md`) no la declara.
- **Alineación del plugin** (`skills/check/scripts/settings_alignment.py`): `/check` lo corre desde la raíz del proyecto y escribe en "Pruebas" la línea `Alineación del plugin: ok | <resumen>`. Solo lee el `.claude/settings.json` del proyecto (no `settings.local.json` ni la configuración de usuario) y lo compara con `references/ask-rules.json`, la fuente única de las reglas `ask`, sin importar el orden:
  - **Faltan:** reglas del plugin que el proyecto no declara.
  - **Extra (info):** reglas `ask` del proyecto que no están en la lista del plugin. Pueden ser propias o viejas que el plugin quitó (`gh api graphql:*`); no cuentan como desalineación.
  - **Plugin y marketplace:** `enabledPlugins` con `stepwise@stepwise: true` y `extraKnownMarketplaces.stepwise` con `ref: main`.
  - **Códigos de salida:** 0 alineado, 1 desalineado (falta una regla, el plugin o el `ref: main`), 2 el archivo no existe, no es JSON válido o tiene una estructura inválida. Salida en 5 líneas como máximo.
  - **Es un aviso, no un fallo:** no frena `/check` ni gasta intentos, y `/check` nunca edita `.claude/settings.json`. En este repo avisa siempre por el plugin y el marketplace, porque se instala en alcance `local` y no los declara (ver [Developing stepwise](../../README.md#developing-stepwise)).
- **Corrida de tests** (`scripts/run_tests.py`): `python3 <ruta>/scripts/run_tests.py full | step <rutas o ids...>` desde la raíz del proyecto. Solo lee y nunca escribe archivos.
  - **Modos:** `full` corre `Tests (full)`. `step` corre `Tests (step)` más las rutas, módulos o ids, que son obligatorios; cada uno cumple `[A-Za-z0-9_./:\[\]][A-Za-z0-9_./:\[\]-]*`, sin `-` inicial ni sintaxis de shell. El comando sale **solo** del `CLAUDE.md` del directorio de trabajo y corre una vez, tal cual, sin `cd` ni prefijos.
  - **Shell:** el de la herramienta Bash de Claude Code, con `-c`. En Windows usa `CLAUDE_CODE_GIT_BASH_PATH` (si existe y se llama `bash.exe`, `sh.exe`, `bash` o `sh`), si no `SHELL` (una ruta absoluta que existe). Nunca busca `bash` en el `PATH` ni usa `System32\bash.exe` (WSL); sin ninguno de los dos, `shell not found`. En macOS y Linux, `SHELL` o `/bin/sh`.
  - **Timeout propio de 570 s**, por debajo de los 600 s de una llamada de Bash (`--timeout <s>` solo para tests). Al vencer, mata el árbol de procesos (`killpg` en POSIX, `taskkill /T /F` en Windows) y reporta `timeout after <N> s`. No limpia contenedores ni otros recursos del stack: un `docker compose run` cortado deja el contenedor vivo hasta que termine su proceso. **Límite:** una suite que tarda más de 570 s, contando el build si el comando lo incluye (por ejemplo, un `docker compose run --build`), no cabe en `test-runner`: hay que correrla a mano.
  - **Reporte**, en 10 líneas como máximo: `Command:`, `Totals:`, `Failures:` (5 como máximo, `- <file>::<test> — <file>:<line>: <error>`) y `Note:`. Lee pytest (con y sin `-q`, `-rfE`, errores de colección), unittest y Karma (la línea `TOTAL:`, con los totales y los saltados de la última línea `Executed <x> of <y>` y los fallos `<navegador> <test> FAILED`). Antes de leer y de reportar, quita los códigos ANSI (`ESC[` + parámetros + una letra) de cada línea, también en el modo genérico. En un `&&`, el resumen k va al comando k (hasta 6 comandos; con más, un total único y una nota): un comando que falla sin resumen sale `not available (exit N)` y los siguientes `not run`.
  - **Modo genérico:** cualquier otro runner (Jest, `flutter test`) da `Totals: not available (exit N)`, la nota `runner not recognized` y las últimas líneas de la salida. Así el plugin no depende del stack.
  - **Códigos de salida:** el del comando de tests; 124 si vence el timeout; 2 si no corrió nada (falta la sección o la clave, `step` sin rutas, una ruta o un timeout inválidos, sin shell); 0 si la clave vale `none`.
  - **Aprobación:** como `fingerprint.py`, pasa por el permiso normal; nada lo aprueba por coincidir con el contrato. Los comandos del contrato corridos a mano también piden confirmación y salen sin recorte: el recorte lo da el reporte del script. Quien revisa un PR mira cualquier cambio en `## Project commands`, porque el script corre lo que diga el `CLAUDE.md`.
- **Tests fuera de la suite principal:** `Tests (full)` los encadena (`cmd1 && cmd2`), y `test-runner` da los totales de cada comando.
- **El `total` de `test-runner`:** el que da el runner (por ejemplo `Ran N tests`); si no lo da, `passed + failed + errors + skipped + xfailed + xpassed`, sin `deselected` ni `warnings`.
- **`Lint/format` sin archivos:** un comando acotado a ciertos archivos (por ejemplo, los `*.py` del diff) que no encontró ninguno debe imprimir la línea exacta `no files to check` y terminar en 0. `/implement`, `/check` y `/close` lo reportan entonces `sin archivos que revisar` en lugar de `ok`; no es un fallo. Sin esa línea, un 0 es `ok`. Por ejemplo: `[ -z "$files" ] && echo "no files to check" || <lint> $files`.
- **Rama del paso:** `/implement`, `/check`, `/audit` y `/close` la interpretan con `^(?P<feature>.+)-step-(?P<n>\d+)$`, tomando la última aparición: `multi-step-form-step-2` es la feature `multi-step-form` y el paso 2.
- **Bloques compartidos** (`tests/test_shared_blocks.py`): algunas instrucciones se repiten a propósito en varias skills, porque dentro de cada skill son más fiables que un archivo común que el modelo puede no leer. Cada copia va entre `<!-- shared:<id> -->` y `<!-- /shared:<id> -->`, en líneas propias o dentro de la línea.
  - **Regla:** un bloque compartido se edita en todas sus copias, en el mismo cambio. El test lee `skills/*/SKILL.md` y `agents/*.md` y lo comprueba: falla si las copias de un `<id>` difieren (sin contar los espacios al final de línea; la sangría cuenta), si un marcador no tiene pareja, si los marcadores se anidan o se solapan, si un `<id>` aparece en un solo archivo o si no hay ningún bloque o ningún archivo. El mensaje nombra el `<id>` y cada versión como `ruta:línea`.
  - **Hoy:** `project-commands` (audit, check, close, implement, spec), `test-runner-foreground` (audit, check, close, implement), `git-rules` y `push-https` (close, spec).
  - **Agregar uno:** envolver todas las copias con el mismo `<id>` (kebab-case); el test lo toma solo. Una copia sin marcadores no se comprueba.
  - **Los comentarios llegan al modelo:** Claude Code no los quita del texto de la skill. En una prueba con `claude -p --plugin-dir`, el modelo no los mencionó ni cambió su respuesta.
- `hooks/block_inplace_edits.py` (`Bash|PowerShell`): niega ediciones de archivos del proyecto desde la shell (`sed -i`, `perl -i`, redirecciones, heredocs, `tee`, `Set-Content`, `Out-File`…) y scripts que escriben archivos. Pide usar Edit o Write.
- `hooks/block_env_access.py` (`Read|Grep|Glob|Edit|MultiEdit|Write|Bash|PowerShell`): niega el acceso a `.env` y `.env.*`, salvo plantillas (`.env.example`, `.env.sample`, `.env.template`, `.env.dist`). En Bash y PowerShell niega cualquier comando que nombre uno (`cat .env`, `Get-Content .env`, `python -c "open('.env')"`, `cp .env.example .env`…), con o sin comillas y en cualquier ruta. No confunde `.venv/`, `environment.py`, `.envrc`, `env.py`, `ENV_VAR=1` ni `printenv`. El motivo pide nombrar la variable y pedirle el valor al usuario.
  - **Falsos positivos aceptados:** lee el texto completo del comando, así que también niega un comando que solo *menciona* el nombre: `git commit -m "... .env ..."`, `gh pr create --title "... .env ..."`, `grep -rn '\.env' src`. Los mensajes, títulos y cuerpos van por archivo (`git commit -F <archivo>`, `--body-file`) o sin el nombre literal.
  - **Límite:** es una barrera contra errores, no un límite de seguridad. Un programa que lee `.env` por dentro (`manage.py runserver`, `docker compose up`, un script propio) no se detecta, ni un nombre armado en tiempo de ejecución. Si el riesgo importa, los secretos reales no viven en el árbol del proyecto.

- `hooks/ask_gh_api_writes.py` (`Bash|PowerShell`): responde `ask` ante un `gh api` que escribe, solo o dentro de `&&`, `;`, `|` o `$(...)`. Cuenta como escritura un método distinto de `GET` (`-X`, `-XPATCH`, `--method`, `--method=`, antes o después de la ruta); también `-f`, `-F`, `--field`, `--raw-field` o `--input` sin `-X GET`, y `graphql` con una `mutation` o una query leída de un archivo. El motivo muestra el método y la ruta. Deja pasar las lecturas y los comandos que solo mencionan `gh api` entre comillas. Las reglas `ask` de `gh api` en `.claude/settings.json` quedan como respaldo (ver el ADR §3.2).
  - **Límite:** no ve un `gh api` armado en tiempo de ejecución ni dentro de `sh -c`. En modo `dontAsk`, un `ask` se deniega.

### Proyectos sin tests automáticos
Si el proyecto no tiene tests (por ejemplo, un frontend sin suite), declara `Tests (step): none` y `Tests (full): none`:
- `/implement` avisa que el paso queda sin test automático y, por cada CA, escribe en la trazabilidad (`## Pruebas` → `### Verificación manual`) los pasos, el resultado esperado y el obtenido. La ejecuta si puede o la deja `pendiente` para que la confirme el usuario, y lo dice. Lint y tipos corren igual si no son `none`.
- En un bug, la reproducción manual se registra en `## Evidencia de regresión` antes del arreglo (falla) y después (pasa).
- `/check` salta la suite, lo anota en `## Pruebas` y corre lo demás que no sea `none`.
- `code-reviewer` acepta un CA con verificación manual registrada; un CA sin test y sin verificación es `blocker`.
- `/close` no mergea con una verificación `pendiente`, salvo que el usuario lo diga.
- Una verificación que solo puede correr después del merge (necesita la rama mergeada, un deploy o el propio `/close`) se marca `después del merge`, con el motivo. No frena el merge del paso: `/close` la agrega como casilla al PR principal, y el último `/close` no saca ese PR de draft hasta que esté marcada.

### CA manuales en un proyecto con tests
Un CA sin un test razonable (un paso que solo toca configuración o documentación, o algo que solo puede correr el usuario) se marca en el ADR: `**CA-<n> (manual: <motivo>):**`.
- `/spec` propone la marca y la lista en el resumen de aprobación; el usuario la aprueba con el ADR. Sin motivo no vale.
- `/implement` escribe para ese CA la verificación manual de arriba en lugar del test; los demás CA del paso siguen con test.
- `code-reviewer` acepta el CA marcado si tiene su entrada; un CA sin marca y sin test sigue siendo `blocker`.
- Si la verificación necesita una skill (`/stepwise:audit pr <num>`), queda `pendiente` con el comando exacto en `Pasos`, y `/implement` pide que lo escribas. `/close` no mergea hasta que lo confirmes.

Los hooks usan solo la biblioteca estándar (Python 3.10 o superior) y corren con `python3` (en Windows, en Git Bash). Tests: `python3 -m unittest discover plugins/stepwise/hooks/tests -v`, `python3 -m unittest discover plugins/stepwise/skills/close/scripts/tests -v`, `python3 -m unittest discover plugins/stepwise/skills/check/scripts/tests -v`, `python3 -m unittest discover plugins/stepwise/scripts/tests -v` (`run_tests.py`, con salidas reales de pytest, unittest y Karma como fixtures, y pares de pytest con y sin `--color=yes`) y `python3 -m unittest discover tests -v` (longitud de rutas, bloques compartidos y versión del plugin) desde la raíz de este repo. Los scripts de las skills (`fingerprint.py`, `settings_alignment.py`) y `scripts/run_tests.py` siguen las mismas reglas.

## Versionado
Versión actual: `1.1.0`, en `.claude-plugin/plugin.json`, y solo ahí: la entrada de `stepwise` en `.claude-plugin/marketplace.json` no lleva `version`.

- **Por qué importa:** Claude Code compara la `version` para saber si hay una actualización. Un cambio publicado en `main` sin subirla no llega a los proyectos, ni con `autoUpdate: true`.
- **API pública:** las claves de `## Project commands`, los nombres de las skills y de los agentes, y el comportamiento que documenta este README.
- **SemVer:**
  - **mayor:** quitar o renombrar una clave, volver obligatoria una opcional, quitar o renombrar una skill o un agente, o cambiar un comportamiento documentado de forma que un proyecto tenga que tocar su configuración;
  - **menor:** una clave opcional nueva, una skill, un agente o un hook nuevos, o un aviso nuevo que no bloquea;
  - **parche:** arreglos y cambios de texto que no cambian el comportamiento documentado, incluidos los tests dentro de `plugins/stepwise/`.
- **Ejemplo:** agregar una clave opcional a `## Project commands` es menor; retirarla después es mayor, porque los proyectos que la declaran tienen que quitarla de su `CLAUDE.md`.
- **Cuándo se sube:** cualquier cambio en `plugins/stepwise/` respecto de la última publicación, aunque sea un test o un texto, exige una `version` distinta. La sube la primera feature que toca el plugin después de publicar; una feature posterior del mismo ciclo la vuelve a subir si su cambio es de un nivel mayor (por ejemplo, de `1.0.1` a `1.1.0`). Cada feature que cambia el plugin agrega su línea en `[Unreleased]` del [CHANGELOG](../../CHANGELOG.md), y la publicación la renombra a la versión.
- **El test** (`tests/test_plugin_version.py`, en la suite de este repo): falla si `plugins/stepwise/` cambió y la `version` no, respecto del tag `stepwise--v*` de versión más alta. Sin tags, compara contra `origin/main`; sin ninguno de los dos, se salta. Compara el árbol de trabajo, con los archivos sin seguimiento, y no hace `fetch`: antes de correrlo, `git fetch --tags origin`. Después de cada publicación, el `/check` de la primera feature que toque el plugin falla hasta que suba la versión: es el recordatorio.
- **Publicar:** con el cambio mergeado en `main` (con `--merge`), el tag anotado sobre ese commit de `main` y su push (pide confirmación por la regla `ask`):
  ```bash
  git fetch origin main
  git tag -a stepwise--v<versión> origin/main -m "stepwise <versión>"
  git push origin stepwise--v<versión>
  ```
  `<plugin>--v<versión>` es la convención de Claude Code para los tags de un plugin. `/close` no crea tags.

## Instalación
```bash
claude plugin marketplace add juanpa1601/stepwise
claude plugin install stepwise@stepwise
```
En alcance `user` y desde `main`. Reinicia la sesión después de instalar. Los detalles (proyecto, problemas conocidos) están en la [Instalación del README raíz](../../README.md#installation). Las skills aparecen como "User only · locked": solo las invoca la persona (`/stepwise:<skill>`). Para trabajar en este repo, mira [Developing stepwise](../../README.md#developing-stepwise). Para probar cambios: `claude --plugin-dir <ruta>/plugins/stepwise`.

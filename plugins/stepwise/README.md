# stepwise

Detailed reference for the `stepwise` plugin: the step-by-step development workflow with Claude Code, with branches and Sub-PRs, per-step traceability, agents and hooks. The introduction is in the [root README](../../README.md), and the design decisions are in [the decisions document](../../docs/decisions/bootstrap/business-rules.md).

The pieces don't read any configuration of their own: they delegate to `## Project commands` in the project's `CLAUDE.md` and, if a value is missing, they stop and propose the line.

The skills write the ADRs, the traceability files and the PRs in Spanish, so the section names and markers they write (for example `## Pruebas`, `### Tests del paso`, `ninguno`, `pendiente`, `después del merge`) are quoted here verbatim.

## Contents
- `agents/test-runner.md` (Haiku; Bash): thin agent. With the modes `step <paths>` (`Tests (step)`) and `full` (`Tests (full)`), it makes a single foreground call to `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/run_tests.py" <mode> [paths]` and returns its output unchanged. It doesn't read `CLAUDE.md` or parse anything: the contract, the run, the timeout and the report belong to the script (see **Test run**). If Claude Code moves its Bash to the background (after 180 s in interactive, VS Code or CLI sessions; not in `claude -p`), it waits for the notice that it finished and reads the end of the output with `tail -n 20`. `${CLAUDE_PLUGIN_ROOT}` is substituted by Claude Code in the agent's body; it isn't in the Bash environment.
- `agents/explore.md` (Sonnet; Read, Grep, Glob): read-only searches, without a shell. It returns conclusions with `path:line`, in 30 lines at most.
- `agents/code-reviewer.md` (Opus; Read, Grep, Glob, read-only Bash): reviews a diff (local or `gh pr diff`) against the feature's ADR, the `CLAUDE.md` and the `README.md` of the folders it touches. It checks criteria without tests, bugs, security, external calls inside transactions, concurrency, conventions and scope. It returns `blocker`, `suggestion` or `question` findings with `path:line` and a fix, in 60 lines at most. On the second pass it reviews only the fixes it receives. It never edits, commits or publishes. Bash is read-only only through its instructions, because `tools` doesn't restrict by pattern.
- `skills/spec/` (`/spec <description>`): classifies the request (feature, bug or new step), investigates with `explore`, interviews only about what the code doesn't answer (4 questions per round; in `-p`, in plain text) and writes the ADR with its template (`references/decision-template.md`): `CA-n` (acceptance criteria) in Dado / Cuando / Entonces (Given / When / Then), steps with their CAs, out of scope, risks and open decisions, in 150 lines at most. Once approved, it creates `<feature>` from `Base branch` without upstream (`--no-track`), commits and pushes the ADR and opens the main PR as a draft (with a remote that isn't GitHub, it skips that). It never writes code.
  - **Request prompt** (optional key `- Prompts: docs/prompts/<feature>/`): after approval, `/spec` writes the exact text it was invoked with, without summarizing or trimming it, to `<Prompts>/<YYYY-MM-DD>-spec.md` (feature or bug) or `<YYYY-MM-DD>-spec-step-<n>.md` (new step; `<n>` is the first step it adds). On top goes a header with the date, the type, the branch and the link to the ADR. It goes in the same commit as the ADR, and "Fuente / Documento" links it.
    - If the file already exists, it doesn't overwrite it: it stops before the commit and asks whether to overwrite it, use another name or not save it.
    - It doesn't look at the path length: the limit belongs to each project (in this repo, `tests/test_path_lengths.py`).
    - Without the key, it saves nothing; the approval summary and the report say so in one line.
- `skills/implement/` (`/implement <n>`): checks the tree, the `<feature>` branch, the step and that the previous one is merged; creates `<feature>-step-<n>`. For each CA, test first (for a bug, it saves the evidence that the regression CA fails before the fix and which ones passed), then the code, and the step's tests with `test-runner`, whose paths it records in `## Pruebas` → `### Tests del paso` (or `ninguno`) for `/check` and `/close`; with `Tests (step): none`, or for a CA marked `(manual: <motivo>)`, a manual verification (see below). It runs `Lint/format` and `Type check`. If the ADR has a gap, it stops and proposes the change. If the step adds, deletes or changes something in `.claude/agents/`, `.claude/skills/` or `.claude/commands/`, the report asks to open a new session, because the session keeps loading the old ones. It doesn't commit.
- `skills/check/` (`/check`): only the step's tests, never the full suite: the `### Tests del paso` list with `test-runner step`; if the list is missing (a step from an older version), it builds it from the test files among the step's changes and asks for confirmation; with `ninguno`, it runs no tests and records `sin tests del paso`. Then `Migrations check`, `Lint/format` and `Type check`; a failure in any of them is a failure of the step. If something fails, it fixes only what belongs to the step (a test the fix touches goes into the list), reruns `Lint/format` and `Type check`, with 3 attempts at most, and asks before touching a failure that looks pre-existing. When it passes, it writes the "Pruebas" section of the traceability with the step's fingerprint (and, with `Docs paths`, the code fingerprint) and the plugin alignment (see below), without committing.
- `skills/audit/` (`/audit self | comments [<num>] | pr <num>`):
  - `self`: the step's local diff with `code-reviewer`; it fixes the `blocker`s, asks once about the suggestions and questions, reviews only the fixes in a second pass and writes "Code review" in the traceability. A test that a fix creates or modifies goes into `### Tests del paso`. `/close` runs it.
  - `comments`: fetches the PR's unresolved comments with `gh` (by default, the main PR), checks them against the code and classifies them as `válido` (valid), `no aplica` (doesn't apply) or `requiere decisión` (needs a decision). Once approved, the valid ones become an "Atender review" step in the ADR (open PR) or a new feature with `/spec` (merged PR).
  - `pr <num>`: reviews someone else's PR and drafts inline comments and a summary; the user picks the verdict.
  - It never publishes on GitHub without explicit approval.
- `skills/close/` (`/close`): requires in "Pruebas" the test line that `/check` writes (or the `Suite completa` line of an older `/check`) and `### Tests del paso`, unless `Tests (step): none` (if they are missing, it asks for `/check`). It runs `/audit self`, unless its last round has the same fingerprint and no open `blocker`. If the fingerprint changed since `/check`, it reruns the step's tests (not the full suite), `Migrations check`, `Lint/format` and `Type check` before committing; if only `Docs paths` paths changed (see the code fingerprint), it runs only `Lint/format` and `Type check`. It completes the traceability with its templates (`references/`), makes one commit, pushes without `-u`, opens the Sub-PR to `<feature>`, merges it with `--merge` and ticks the step in the main PR, with the `después del merge` verifications as checkboxes. On the last step it writes the main PR description (it asks before applying it), with "Verificación Global" set to `pendiente de /regression`, and leaves it in draft: only `/regression` takes it out. Its report ends with `next: /regression`. With a remote that isn't GitHub, it pushes, warns and skips the `gh` steps.
- `skills/regression/` (`/regression`): the only skill that runs `Tests (full)` and the only one that takes the main PR out of draft. It runs on `<feature>`, not on a step branch, with a clean tree, up to date with `origin/<feature>` and with every step of the ADR merged (main PR checkboxes; without GitHub, step branches that are ancestors of `<feature>`).
  - **Run:** the main session, not `test-runner`, launches `python3 <plugin>/scripts/run_tests.py full --timeout 3600` in the background (`run_in_background`) and waits for the notice without `sleep` or polling. The 600 s cap applies to foreground calls, so 20- or 30-minute suites fit. With `timeout after 3600 s`, or if the background isn't available or doesn't notify, it gives the user the `Tests (full)` command to run by hand and records `Ejecutó: usuario` (run by the user).
  - **Green:** checks that `origin/<feature>` is still at the tested commit and writes `regression.md` in the `Traceability` folder (tested commit, command, totals, who ran it), with a direct commit on `<feature>` and its push. It proposes "Verificación Global" in the main PR body and asks before `gh pr ready`. It doesn't offer it while a `Verificación después del merge` is still unticked or an installation section is still unfilled (unless there is an explicit decision, which is recorded in `regression.md`), or if a commit arrived after `regression.md`.
  - **Red:** it never fixes on `<feature>`. It diagnoses each failure, finds the step that introduced it with `git log` and hands over the line `/stepwise:spec <feature> Paso de corrección: ...`. It asks whether to leave a failure that looks like it comes from `Base branch`.
- **Step fingerprint** (`skills/close/scripts/fingerprint.py`): sha256 of the diff against `<feature>` with the untracked files, without the traceability or the ADR. Read-only. `/check` records it (in "Pruebas") and so does each `/audit self` round (in "Code review"); `/close` recomputes it to avoid repeating work on the same diff.
  - **Code fingerprint** (`--docs <pathspecs>`): with the optional key `- Docs paths: '*.md' 'docs/**'` in `## Project commands` (simple git pathspecs, without magic such as `:(glob)` or `:!`: the script rejects them), `/check` also records `Huella de código` (code fingerprint), which leaves those paths out. The root `CLAUDE.md` always counts, because it holds the contract. If after `/check` only those paths changed, `/close` doesn't rerun the step's tests or `Migrations check`. Without the key, nothing changes.
  - **What goes in `Docs paths`:** only paths that no test, code lint or migration reads. A project where `.md` files are part of the product (like this repo, whose skills and agents are `.md`) doesn't declare it.
- **Plugin alignment** (`skills/check/scripts/settings_alignment.py`): `/check` runs it from the project root and writes in "Pruebas" the line `Alineación del plugin: ok | <resumen>`. It only reads the project's `.claude/settings.json` (not `settings.local.json` or the user configuration) and compares it with `references/ask-rules.json`, the single source of the `ask` rules, regardless of order:
  - **Missing** (`Faltan`): plugin rules the project doesn't declare.
  - **Extra (info):** project `ask` rules that aren't in the plugin's list. They can be the project's own or old ones the plugin removed (`gh api graphql:*`); they don't count as misalignment.
  - **Plugin and marketplace:** `enabledPlugins` with `stepwise@stepwise: true` and `extraKnownMarketplaces.stepwise` with `ref: main`.
  - **Exit codes:** 0 aligned, 1 misaligned (a rule, the plugin or `ref: main` is missing), 2 the file doesn't exist, isn't valid JSON or has an invalid structure. Output in 5 lines at most.
  - **It is a warning, not a failure:** it doesn't stop `/check` or use up attempts, and `/check` never edits `.claude/settings.json`. In this repo it always warns about the plugin and the marketplace, because the plugin is installed in `local` scope and they aren't declared (see [Developing stepwise](../../README.md#developing-stepwise)).
- **Test run** (`scripts/run_tests.py`): `python3 <path>/scripts/run_tests.py full | step <paths or ids...>` from the project root. Read-only; it never writes files.
  - **Modes:** `full` runs `Tests (full)`. `step` runs `Tests (step)` plus the paths, modules or ids, which are required; each one matches `[A-Za-z0-9_./:\[\]][A-Za-z0-9_./:\[\]-]*`, without a leading `-` or shell syntax. The command comes **only** from the `CLAUDE.md` of the working directory and runs once, as is, without `cd` or prefixes.
  - **Shell:** the one of Claude Code's Bash tool, with `-c`. On Windows it uses `CLAUDE_CODE_GIT_BASH_PATH` (if it exists and is named `bash.exe`, `sh.exe`, `bash` or `sh`), otherwise `SHELL` (an absolute path that exists). It never looks for `bash` on the `PATH` or uses `System32\bash.exe` (WSL); without either of them, `shell not found`. On macOS and Linux, `SHELL` or `/bin/sh`.
  - **Its own 570 s timeout**, below the 600 s of a Bash call (`--timeout <s>`: passed by the `run_tests.py` tests and by `/regression`, nobody else). When it expires, it kills the process tree (`killpg` on POSIX, `taskkill /T /F` on Windows) and reports `timeout after <N> s`. It doesn't clean up containers or other stack resources: an interrupted `docker compose run` leaves the container alive until its process ends. **Limit:** since `2.0.0`, `/check` and `/close` no longer run the full suite: `/regression` runs it, in the background and with `--timeout 3600`. The 570 s stay for `test-runner`, which runs the step's tests: if they take longer, counting the build if the command includes it (for example, a `docker compose run --build`), they don't fit and have to be run by hand.
  - **Report**, in 10 lines at most: `Command:`, `Totals:`, `Failures:` (5 at most, `- <file>::<test> — <file>:<line>: <error>`) and `Note:`. It reads pytest (with and without `-q`, `-rfE`, collection errors), unittest and Karma (the `TOTAL:` line, with the totals and the skipped ones from the last `Executed <x> of <y>` line and the `<browser> <test> FAILED` failures). Before reading and reporting, it strips ANSI codes (`ESC[` + parameters + a letter) from each line, also in generic mode. In an `&&`, summary k goes to command k (up to 6 commands; with more, a single total and a note): a command that fails without a summary comes out as `not available (exit N)` and the following ones as `not run`.
  - **Generic mode:** any other runner (Jest, `flutter test`) gives `Totals: not available (exit N)`, the note `runner not recognized` and the last lines of the output. That way the plugin doesn't depend on the stack.
  - **Exit codes:** that of the test command; 124 if the timeout expires; 2 if nothing ran (the section or the key is missing, `step` without paths, an invalid path or timeout, no shell); 0 if the key is `none`.
  - **Approval:** like `fingerprint.py`, it goes through the normal permission; nothing approves it for matching the contract. The contract's commands run by hand also ask for confirmation and come out untrimmed: the trimming comes from the script's report. Whoever reviews a PR looks at any change in `## Project commands`, because the script runs whatever the `CLAUDE.md` says.
- **Tests outside the main suite:** `Tests (full)` chains them (`cmd1 && cmd2`), and the `run_tests.py` report (in `/regression`) gives the totals of each command.
- **The `test-runner` `total`:** the one the runner gives (for example `Ran N tests`); if it doesn't give one, `passed + failed + errors + skipped + xfailed + xpassed`, without `deselected` or `warnings`.
- **`Lint/format` with no files:** a command limited to certain files (for example, the `*.py` files of the diff) that found none must print the exact line `no files to check` and exit with 0. `/implement`, `/check` and `/close` then report it as `sin archivos que revisar` (no files to check) instead of `ok`; it isn't a failure. Without that line, a 0 is `ok`. For example: `[ -z "$files" ] && echo "no files to check" || <lint> $files`.
- **Step branch:** `/implement`, `/check`, `/audit`, `/close` and `/regression` (which stops on one) interpret it with `^(?P<feature>.+)-step-(?P<n>\d+)$`, taking the last occurrence: `multi-step-form-step-2` is the feature `multi-step-form` and step 2.
- **Shared blocks** (`tests/test_shared_blocks.py`): some instructions are repeated on purpose in several skills, because inside each skill they are more reliable than a common file the model may not read. Each copy goes between `<!-- shared:<id> -->` and `<!-- /shared:<id> -->`, on their own lines or inline.
  - **Rule:** a shared block is edited in all its copies, in the same change. The test reads `skills/*/SKILL.md` and `agents/*.md` and checks it: it fails if the copies of an `<id>` differ (not counting trailing spaces; indentation counts), if a marker has no pair, if markers nest or overlap, if an `<id>` appears in a single file, or if there are no blocks or no files. The message names the `<id>` and each version as `path:line`.
  - **Today:** `project-commands` (audit, check, close, implement, regression, spec), `test-runner-foreground` (audit, check, close, implement), `step-tests` (check, close), `git-rules` and `push-https` (close, regression, spec).
  - **Adding one:** wrap every copy with the same `<id>` (kebab-case); the test picks it up on its own. A copy without markers isn't checked.
  - **The comments reach the model:** Claude Code doesn't strip them from the skill's text. In a test with `claude -p --plugin-dir`, the model didn't mention them or change its answer.
- `hooks/block_inplace_edits.py` (`Bash|PowerShell`): denies edits to project files from the shell (`sed -i`, `perl -i`, redirections, heredocs, `tee`, `Set-Content`, `Out-File`…) and scripts that write files. It asks to use Edit or Write.
- `hooks/block_env_access.py` (`Read|Grep|Glob|Edit|MultiEdit|Write|Bash|PowerShell`): denies access to `.env` and `.env.*`, except templates (`.env.example`, `.env.sample`, `.env.template`, `.env.dist`). In Bash and PowerShell it denies any command that names one (`cat .env`, `Get-Content .env`, `python -c "open('.env')"`, `cp .env.example .env`…), with or without quotes and in any path. It doesn't confuse `.venv/`, `environment.py`, `.envrc`, `env.py`, `ENV_VAR=1` or `printenv`. The reason asks to name the variable and ask the user for the value.
  - **Accepted false positives:** it reads the full text of the command, so it also denies a command that only *mentions* the name: `git commit -m "... .env ..."`, `gh pr create --title "... .env ..."`, `grep -rn '\.env' src`. Messages, titles and bodies go through a file (`git commit -F <file>`, `--body-file`) or without the literal name.
  - **Limit:** it is a guard against mistakes, not a security boundary. A program that reads `.env` internally (`manage.py runserver`, `docker compose up`, a script of your own) isn't detected, nor is a name built at runtime. If the risk matters, real secrets don't live in the project tree.

- `hooks/ask_gh_api_writes.py` (`Bash|PowerShell`): answers `ask` on a `gh api` that writes, alone or inside `&&`, `;`, `|` or `$(...)`. A method other than `GET` counts as a write (`-X`, `-XPATCH`, `--method`, `--method=`, before or after the path); so do `-f`, `-F`, `--field`, `--raw-field` or `--input` without `-X GET`, and `graphql` with a `mutation` or a query read from a file. The reason shows the method and the path. It lets reads through, and commands that only mention `gh api` in quotes. The `gh api` `ask` rules in `.claude/settings.json` remain as a backup (see ADR §3.2).
  - **Limit:** it doesn't see a `gh api` built at runtime or inside `sh -c`. In `dontAsk` mode, an `ask` is denied.

### Projects without automated tests
If the project has no tests (for example, a frontend without a suite), it declares `Tests (step): none` and `Tests (full): none`:
- `/implement` warns that the step has no automated test and, for each CA, writes in the traceability (`## Pruebas` → `### Verificación manual`) the steps, the expected result and the actual one. It runs it if it can or leaves it `pendiente` (pending) for the user to confirm, and says so. Lint and types run anyway if they aren't `none`.
- For a bug, the manual reproduction is recorded in `## Evidencia de regresión` before the fix (fails) and after it (passes).
- `/check` skips the step's tests, records that in `## Pruebas` and runs everything else that isn't `none`. With `Tests (full): none`, `/regression` doesn't run anything either: it records that and moves on to the ready.
- `code-reviewer` accepts a CA with a recorded manual verification; a CA without a test and without a verification is a `blocker`.
- `/close` doesn't merge with a `pendiente` verification, unless the user says so.
- A verification that can only run after the merge (it needs the merged branch, a deploy or `/close` itself) is marked `después del merge` (after the merge), with the reason. It doesn't block the step's merge: `/close` adds it as a checkbox to the main PR, and `/regression` doesn't take that PR out of draft until it is ticked.

### Manual CAs in a project with tests
A CA without a reasonable test (a step that only touches configuration or documentation, or something only the user can run) is marked in the ADR: `**CA-<n> (manual: <motivo>):**`.
- `/spec` proposes the mark and lists it in the approval summary; the user approves it with the ADR. It isn't valid without a reason.
- `/implement` writes the manual verification above for that CA instead of the test; the other CAs of the step still get tests.
- `code-reviewer` accepts the marked CA if it has its entry; a CA without a mark and without a test is still a `blocker`.
- If the verification needs a skill (`/stepwise:audit pr <num>`), it stays `pendiente` with the exact command in `Pasos`, and `/implement` asks you to type it. `/close` doesn't merge until you confirm it.

The hooks use only the standard library (Python 3.10 or later) and run with `python3` (on Windows, in Git Bash). Tests: `python3 -m unittest discover plugins/stepwise/hooks/tests -v`, `python3 -m unittest discover plugins/stepwise/skills/close/scripts/tests -v`, `python3 -m unittest discover plugins/stepwise/skills/check/scripts/tests -v`, `python3 -m unittest discover plugins/stepwise/scripts/tests -v` (`run_tests.py`, with real pytest, unittest and Karma outputs as fixtures, and pytest pairs with and without `--color=yes`) and `python3 -m unittest discover tests -v` (path length, shared blocks, plugin version and that only `/regression` runs the full suite or uses `gh pr ready`) from the root of this repo. The skills' scripts (`fingerprint.py`, `settings_alignment.py`) and `scripts/run_tests.py` follow the same rules.

## Versioning
Current version: `2.0.0`, in `.claude-plugin/plugin.json`, and only there: the `stepwise` entry in `.claude-plugin/marketplace.json` has no `version`.

- **Why it matters:** Claude Code compares the `version` to know whether there is an update. A change published on `main` without bumping it doesn't reach the projects, not even with `autoUpdate: true`.
- **Public API:** the `## Project commands` keys, the names of the skills and agents, and the behavior this README documents.
- **SemVer:**
  - **major:** removing or renaming a key, making an optional key required, removing or renaming a skill or an agent, or changing a documented behavior in a way that forces a project to touch its configuration;
  - **minor:** a new optional key, a new skill, agent or hook, or a new warning that doesn't block;
  - **patch:** fixes and text changes that don't change the documented behavior, including the tests inside `plugins/stepwise/`.
- **Example:** adding an optional key to `## Project commands` is minor; removing it later is major, because the projects that declare it have to remove it from their `CLAUDE.md`.
- **When it is bumped:** any change in `plugins/stepwise/` since the last release, even a test or a text, requires a different `version`. The first feature that touches the plugin after a release bumps it; a later feature in the same cycle bumps it again if its change is of a higher level (for example, from `1.0.1` to `1.1.0`). Each feature that changes the plugin adds its line under `[Unreleased]` in the [CHANGELOG](../../CHANGELOG.md), and the release renames it to the version.
- **The test** (`tests/test_plugin_version.py`, in this repo's suite): fails if `plugins/stepwise/` changed and the `version` didn't, compared with the `stepwise--v*` tag with the highest version. Without tags, it compares against `origin/main`; without either, it is skipped. It compares the working tree, with the untracked files, and doesn't `fetch`: before running it, `git fetch --tags origin`. After each release, the first feature that touches the plugin fails until it bumps the version: that's the reminder. Since `2.0.0`, `/regression` gives it, because it runs `Tests (full)`, or `/check` earlier, if the step lists `tests/test_plugin_version.py` in `### Tests del paso`; that's why the first step that touches `plugins/stepwise/` should list it.
- **Release:** with the change merged into `main` (with `--merge`), the annotated tag on that `main` commit and its push (it asks for confirmation because of the `ask` rule):
  ```bash
  git fetch origin main
  git tag -a stepwise--v<version> origin/main -m "stepwise <version>"
  git push origin stepwise--v<version>
  ```
  `<plugin>--v<version>` is Claude Code's convention for a plugin's tags. `/close` doesn't create tags.

## Installation
```bash
claude plugin marketplace add juanpa1601/stepwise
claude plugin install stepwise@stepwise
```
In `user` scope and from `main`. Restart the session after installing. The details (project setup, known issues) are in the [Installation section of the root README](../../README.md#installation). The skills show as "User only · locked": only the person invokes them (`/stepwise:<skill>`). To work on this repo, see [Developing stepwise](../../README.md#developing-stepwise). To try changes: `claude --plugin-dir <path>/plugins/stepwise`.
